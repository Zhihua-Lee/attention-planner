# Outlook 日历：经 Google Drive 导入

学校的 Outlook 往往不允许把日历发布成订阅链接（.ics），所以换一条路：Power Automate 定时把 Outlook 日程写进你 Google
Drive 里的一个私有文件，Attention Planner 连上同步后读这个文件。只读：应用不会改动你的 Outlook。

```text
学校 Microsoft 365 Outlook
        │  Power Automate（每 30 分钟）
        ▼
你的 Google Drive / outlook-calendar.json（私有）
        │  应用用同步时的 Google 授权读取
        ▼
Attention Planner：NOW 的日程、找时间、AI 的 agenda
```

Outlook 和 Google Drive 可以是不同的账号，这正是为“学校 Outlook + 个人 Google Drive”设计的。

## 一、在应用里准备文件

1. 设置 → 同步与数据 → 同步 → 连接，登录 Google。
2. 设置 → 日历 → Outlook 日历 → 点开“怎么设置 Outlook”。

打开时应用会检查你的 Google Drive：还没有 `outlook-calendar.json` 就新建一个（在“我的云端硬盘”里，不共享），并给它打上
应用认得的标记；已经有了就什么都不做。

为什么要由应用来建：应用的 Google 权限很窄，只能读写它自己建的文件（`drive.file`），看不到你 Drive 里的其他东西。
Power Automate 自己建的文件，应用读不到。所以先由应用建好，再让 Power Automate 每次“更新”这同一个文件。

## 二、在 Power Automate 里建定时流

在 [Power Automate](https://make.powerautomate.com) 用学校账号新建“计划的云端流”，连接学校 Outlook 和你的个人 Google
Drive。只用标准连接器，不需要 Premium。

### 1. 重复（Recurrence）

- 频率：分钟（Minute）
- 间隔：`30`

本教程保持触发器“并发控制”关闭（默认值）。它控制的是**不同次流运行**，不是下面分页循环的执行顺序。
2026-10-06 的恢复测试中，把触发器并发设为 `1` 后，平台提示“检测到触发器并发限制”并跳过新运行；解除限制后测试才跑通。
这不表示所有流都应关闭并发控制，也不保证当前设置不会出现运行重叠。若一次运行超过 30 分钟，应先按下方故障恢复步骤检查积压，
不要靠反复手动测试增加队列。

### 2. 获取事件的日历视图 (V3)：第一页

Office 365 Outlook 的“获取事件的日历视图 (V3)”（Get calendar view of events (V3)）：

- 日历 id：`Calendar`
- 开始时间：`addDays(utcNow(), -30)`
- 结束时间：`addDays(utcNow(), 365)`
- 最大计数（Max Count）：`256`
- 跳过计数（Skip Count）：`0`

它一次最多返回 256 条。只用这一个动作时，流程也会显示“成功”，但超过 256 条的部分会被悄悄截掉，比如某天下午和晚上的日程
不见了。所以要继续分页。

### 3. 初始化变量：存第一页

加一个数组（Array）变量 `AllEventsPaged`，初始值：

```text
body('获取事件的日历视图(V3)')?['value']
```

英文界面或动作名称不同时，从动态内容里选第一个日历动作的 `value`，不要手写名称。

### 4. 应用到每一个（Apply to each）：有需要才读取下一页

输入：

```text
range(1,32)
```

旧配置会无条件请求后续 32 页，即使早已读完也继续访问 Outlook。当前配置仍在云端执行 32 轮条件判断，但在数据不足一页后跳过
后续 Outlook 请求；**不是 Do until，也不是提前退出整个循环**。

循环里的层级必须如下；“选择”和“更新文件”放在循环外：

```text
应用到每一个：range(1,32)，顺序执行
├─ 条件：累计条数 >= 当前循环项 × 256
│  ├─ 真：获取事件的日历视图 (V3)（下一页）
│  └─ 假：留空
├─ 撰写 / 编辑：合并已有数据和本轮结果
└─ 设置变量：AllEventsPaged = 撰写的输出
选择（六个字段）
更新文件（同一个 outlook-calendar.json）
```

1. 添加“条件”。左侧通过 **fx / 插入表达式** 填入：

   ```text
   greaterOrEquals(length(variables('AllEventsPaged')),mul(item(),256))
   ```

   运算符选“等于”；右侧也通过表达式填入 `true`，不要输入普通文本字符串。

2. 在“真”分支中添加另一个“获取事件的日历视图 (V3)”：日历、开始、结束时间和第一页一样；最大计数 `256`；
   跳过计数表达式 `mul(item(),256)`。“假”分支留空。旧的无条件取下一页动作应移入分支或被替换，不要在条件后再保留一份。
3. 在**条件之后、两个分支之外、循环之内**添加数据操作的“撰写”（Compose，旧版中文设计器可能叫“编辑”）：

   ```text
   union(variables('AllEventsPaged'), coalesce(body('获取事件的日历视图(V3)_1')?['value'], json('[]')))
   ```

   `coalesce` 将本轮被跳过动作的空结果变为空数组，保留已经读到的日程。它不是吞掉请求错误：保持默认的“上一操作成功后运行”，
   不要勾选失败或超时后继续，以免把部分数据当成完整导出覆盖文件。

4. “设置变量”：选 `AllEventsPaged`，值为上一步的输出（`outputs('编辑')`，或从动态内容里选）。

**动作名称要以自己的流为准。** 上面的 `_1` 是本次修复新建动作的实际名称，不是通用固定名称；已有流可能是 `_2`，英文界面也
不同。合并表达式必须引用“真”分支内的取数动作，不能仍引用已删除的旧动作。使用表达式编辑器时填代码块中的内容，不额外套引号
或 `@{...}`。切换到代码视图检查字段，确认没有旧表达式残留或重复拼接，然后运行“流检查器”。

例如：第一页只有 100 条时，后续 32 轮均跳过 Outlook 请求；共有 300 条时，先读 256 条，再读 44 条，随后跳过。
若刚好有 256 条，会再请求一次得到空页。这些是分页逻辑示例，不是本次线上测试的实际日程数量。

保持**循环**默认的按顺序执行，不要开并发，否则几轮会同时改同一个变量。上限仍为第一页加 32 页，共 8,448 条；如果最后一页
仍满 256 条，不能据此认定已经读完，应检查是否需要增加页数或缩短范围。本方案使用累计去重条数判断是否继续；若翻页期间日历发生
变化、跨页返回重复项，累计条数可能不足阈值，应重新导出并核对缺失事件，不能把“流成功”当成完整性证明。

### 5. 选择（Select）

数据操作的“选择”。从（From）填 `variables('AllEventsPaged')`，只映射这 6 项：

| 输出键     | 表达式                         |
| ---------- | ------------------------------ |
| `id`       | `item()?['id']`                |
| `title`    | `item()?['subject']`           |
| `start`    | `item()?['startWithTimeZone']` |
| `end`      | `item()?['endWithTimeZone']`   |
| `location` | `item()?['location']`          |
| `allDay`   | `item()?['isAllDay']`          |

不要导出正文、参会人、会议链接或组织者。输出就是一个数组，不用再套一层。

### 6. 更新文件（Update file）

Google Drive 的“更新文件”：

- 文件：选第一部分准备好的 `outlook-calendar.json`。
- 文件内容：“选择”的输出。

不要用“创建文件”：每次都会多出一个同名副本，新文件也没有应用认得的标记，应用读不到。

保存并打开流程，用“流检查器”确认没有错误，再点“测试”手动跑一次。

## 三、回到应用核对

1. 先确认 Power Automate 本次运行整体成功，尤其是最后的 Google Drive“更新文件”成功。“已成功启动”只代表请求被接受。
2. 设置 → 日历 → Outlook 日历 → 刷新，等待请求完成，确认“Power Automate 最近写入”更新到本次测试时间，超过 2 小时的警告消失。
3. 打开 NOW 的日程，抽查标题、时间、地点和全天日程，也检查已知的下午、晚上事件。若缺失，检查分页动作和所选日历；一个日历的
   分页不会自动包含账号下的其他课程或订阅日历。
4. 下一轮定时运行后再检查文件时间是否继续前进。一次手动测试成功不等于长期定时运行已经验证。

“同步与数据”里的“已同步”表示任务数据同步，不是 Outlook 导出成功的凭据；日历应以这里的文件写入时间为准。

应用每次同步后会读一次这个文件，最多 10 分钟一次。手机上的应用在后台不会自己刷新，回到前台或打开时会读到最新的。

## 安全与隐私

- `outlook-calendar.json` 是“我的云端硬盘”里的普通文件，默认私有。不要给它开公开链接或改共享。
- 应用的 `drive.file` 权限只能读写它自己建的文件，不能浏览整个 Drive。
- Power Automate 的 Google Drive 连接由 Microsoft 管理，权限通常比应用的更宽。这是这条路额外要信任的一环：只连接你信任的
  个人 Google 账号，并定期在 Google 账号的“第三方访问”里检查它。
- 文件里只有日程展示需要的 6 项，万一副本泄露，影响也小。
- 不再使用时：先关掉 Power Automate 流，再删除它的 Google Drive 连接和 `outlook-calendar.json`。下次点开“怎么设置
  Outlook”时，应用会重新建一个空文件。

## 常见问题

**文件的更新时间不变**：看 Power Automate 流是否开着、最近一次是否成功，以及“更新文件”是否选的是应用准备的那个文件。

**同一天只有上午的日程**：见上面“回到应用核对”的第 3 条。

**手机会不会每 30 分钟自动刷新**：Power Automate 在云端更新文件，但手机不允许网页应用在后台一直运行。打开应用或切回前台
时会读到最新的。

## 长时间不更新：恢复步骤

1. 先在流详情中确认是这一条 Outlook 导出流，记录配置；如导出恢复用的包，应确认文件实际下载完成，而不只看到“正在下载”。
2. 暂时关闭这条流，停止新增定时运行。查看“所有运行”，区分失败、长时间运行和被跳过；不要只看最新一条是否标成成功。
3. 如果有大量积压，对**这条流**使用“取消所有流运行”，确认后等待取消完成，再刷新列表核对。“取消请求已提交”不等于已全部取消。
   取消运行不是删除 Outlook 日程或 Drive 文件；不要删除已有导出文件来清理积压。
4. 查看卡住的运行详情，定位到具体动作。2026-10-06 排查时，第一页和初始化变量成功，但循环内的下一页读取等待，最后的更新文件
   尚未执行。没有观察到明确的 429 错误，因此不能把限流或配额耗尽当成已证实原因。
5. 按第二部分第 4 步修正分页条件、分支层级和动作引用，保留原来的日历、时间范围、六个字段和目标文件。保存，确认流检查器无错误。
6. 如果出现“检测到触发器并发限制”，先检查尚未结束的运行。本次恢复按平台提示关闭了**触发器**并发控制并成功保存，才恢复新运行；
   不要混同为开启分页循环并发。如果你的设计器拒绝修改，应保留配置并检查具体错误，确认保存成功后再运行，不要立即重建整条流。
7. 重新开启流，只手动测试一次，按上面的四项验收检查。若仍卡住，记录动作、状态和错误后再处理，不要连续点击测试制造更多积压。
